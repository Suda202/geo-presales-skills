# 渲染规范(数据层产出 → 客户 HTML)

数据层把回答正文转成成品 HTML(`answer_html` / `answer_zh_html`),渲染层直接注入。以下规则来自 Bewinch 报告的实战缺陷,改 `assets/report.js`、`assets/report-extra.css` 或 `scripts/build_report_data.py` 的 markdown 转换前必读。

**源码真相在本 skill**:任何视觉修订都改 `scripts/` 与 `assets/`,然后完整重跑数据链(build → attach_sentiment → attach_translations → verify → render)。手改已渲染的 HTML 会在下次重渲染时被静默覆盖,且让产物与 `report-data.json` 脱钩。

## 交付与部署(单文件 HTML 的体积陷阱)

报告是单文件 HTML,内嵌全部数据,**体积天然很大**(Bewinch 案例 5.5MB,其中内嵌数据 4.86MB,gzip 后仍有 1.13MB)。这不是缺陷,但会引起一类**极难排查的「空白页」**——2026-09-20 实际踩过一次:

- **症状**:页面静态骨架正常(能看到模块标题和 KPI 标签),但 KPI 数值是占位符 `—`、筛选按钮整片空白。
- **判断依据(关键)**:文件结构是「静态骨架在前 → 内嵌数据脚本 → 交互脚本」。若 boot 执行过但报错,页首会插入红色「报告渲染中断」提示;**截图里没有这条提示 = 脚本根本没跑到**,即响应被中途截断,不是内容或逻辑问题。
- **排查顺序**:1) 线上字节与本地逐字节比对;2) 用线上相同字节本地渲染,能跑通即排除文件本身;3) 查响应头(Content-Type、CSP、编码);4) 查 CDN 边缘缓存 TTL——实测有节点对这份 HTML 缓存 **TTL 长达一年**,命中过残页副本会一直拿到截断响应,需强制重新部署换 ETag 刷新缓存。
- **交付给客户的预防动作**:告知对方用**无痕窗口**打开(排除浏览器扩展/VPN 代理截断大响应),并**硬刷新 `Cmd + Shift + R`**。对内验证一律用「线上字节 vs 本地字节」逐字节比对,不要只看「部署成功」。可复核的线上地址(如 Netlify)要保留 ETag 记录,便于判断客户端看到的是哪一版。
- **体积优化的方向**(尚未实施,需求出现再做):译文按需加载、内嵌数据压缩、详情抽出为独立文件。

## 正文渲染(顺序敏感)
Markdown 转换的处理顺序不能随意调换,引用 pill 必须在普通链接之前:

1. 先收集脚注定义行 `[N]: url "标题"`,定义行本身从正文移除,但 URL 要留住供 pill 链接。
2. **引用 pill**:`([来源名][N])` 与 `[来源名][N]` 渲染成句尾可点击的 pill,`href` 取脚注 URL,`title` 取来源名;取不到 URL 时降级为不可点击的 `<span>` 而不是丢弃。
3. **Markdown 链接**:URL 里允许一层括号(如 `.../product(tk-cs200-hma)?utm=...`),正则必须容忍,否则链接在首个 `)` 提前闭合、`?utm_source=...)` 漏成可见文本。
4. **表格**:行内 `<br>` 不能换成换行(会把单行表格拆碎、整表退化成裸管道文本),应转成 ` / `;行单元格数**多于**表头时,把溢出格合并进最后一列(前 N-1 列仍对齐),**不要整行丢弃**——实测一条 AIO 回答 80% 正文都在一个超宽行里,丢弃即静默吞内容;少列的行补空。
5. 跨单元格断裂的连续星号(`**LG…/…Wa**`)是碎片,直接删,不要渲染成粗体。

硬约束:

- **Scrapeless 锚点残留文案必须清掉**:采集文本里混着 `Go to product viewer dialog for this item.`,它**紧贴在商品名后**(`AquaTru CarafeGo to product viewer...`),不清会直接交付给客户(实测 329 处、60 条明细、13 个切片),还会在挖词表时造出 `CarafeGo` 这类垃圾 token。清洗时**替换成空格而非删除**,否则两个名字会被粘成一个词。常量 `PRODUCT_VIEWER_NOISE` 在两处定义:渲染层 `build_report_data.py`(用 `normalize_answer_html` 清洗)与判读层 `sentiment_sentences.py`(在 `answer_text` 清洗),两边必须一致——判读层不清的话,情感证据句仍会带着这串 UI 文案上屏。加同类清洗时同步扩这两处,并补 `tests/test_normalize_answer.py` 的回归用例。
- 品牌高亮**不得覆盖 pill 自身的颜色**;高亮规则要在 pill 生成之后排除 pill 内部文本。
- `answer_html` / `answer_zh_html` 已是转义好的成品,渲染层不要再二次转义。

## 商品卡(ChatGPT 商品表)

- **不要**把 `id / goods / price / rating / merchants / picture` 原始表格直接渲染给客户;19 位商品 ID 无意义。
- 用采集的结构化字段 `task_result.products` 渲染成平台风格商品卡:标题、价格、评分、商家。
- 有 `logo` / `image` 就显示,没有就隐藏占位,**不留空白框**。
- 处理 `product[...]` / `entity[...]` 占位 token;`<img src="data:image/jpeg;base64,...">` 这类内联图会撑爆单元格,需保护后再渲染。

## 版式与留白(原型对不上的地方)

原型是给国内报表做的,直接套到本报告上会在几处显得拥挤或失衡,以下为 2026-09-17/18 逐条调过并确认的版式规则:

- **抽屉左右布局**:原型右栏给的是 `minmax(380px, 1fr)`,宽屏下会占去四成、正文被压窄。右栏只放品牌榜和引用列表,改成定宽上限 `minmax(260px, 320px)`,空间让给正文。
- **回答正文留白**:正文面板 `padding: 18px 16px`;回答里的表格包在 `.answer-table-wrap` 里做 `overflow-x: auto`,宽表在容器内**左右可拖**、单元格给 `max-width` 防止单列吃掉整行,窄表仍撑满容器。客户反馈原话:「左右不能拖动,没有留有余地的空白,跟边框靠的太近了」。
- **对齐**:表头与数字列必须对齐(比价、引用份额这类数字列尤其明显),客户两次点名「没对齐」。改完在浏览器里量列宽确认,不要只看截图。
- **颜色饱和度**:新增图表的配色**必须取自报告本身的低饱和土色系**(`--green`、`#9a8660`、`#9a6b61`、`--line`),不要用鲜艳的默认色。客户反馈:「这里的颜色太鲜艳了吧,跟 html 本身的风格和配色体系不搭」。
- **分色只改指定的那一处**:客户圈注「灰色字体改成黑色」时,只改圈中的文本色,**其余仍保持正绿负红**——不要顺手统一整块的颜色。反过来也一样:主题矩阵里「无数据 `—`」用黑、Theme 列与非目标品牌表头用黑,而正负向单元格保持绿/红。
- **品牌名不全部大写**:榜单与情感条的品牌名去掉 `text-transform: uppercase`,与其他位置一致。表头类的全大写是设计,品牌名不是。
- **抽屉内不放冗余元信息**:每页已能看出的「地区 / 平台」这类字段不必在抽屉里重复展示。

## 引用展示

- **一个 pill 折叠多个 URL**:Google 系平台(AIO/overview)会在一个 pill 里折叠多个来源,ChatGPT 没有这个现象。渲染按平台形态走,不强行统一。
- **多 pill 并列时不去重**:正文里同一来源出现多次就渲染多个 pill,**引用次数按 pill 实例计数**——计数要能对着原始数据验,去重会让客户无法复核(曾实现过折叠/去重,已按客户要求回滚)。
- **引用来源区只展示 URL,不展示页面 title**;URL 与 icon 同行、单行截断。
- **hover 必须显示完整 URL**:曾出现 hover 只显示一个 `?` 图标(hover 内容没渲染出来),客户两次反馈。hover 里可以补 title,但不能只有图标。
- 「官网当前被引用的页面共 N 个」这类说明句不展示。
- 抽屉里该条回答的引用份额标签直接写「引用份额」,不写「本回答引用份额」。
- 引用明细按 canonical URL 去重(同一 URL 的不同片段不重复列),但正文 pill 次数不去重——两者是不同层级的展示。

## 交互与文案

- **品牌显示名精简**:数据层的 key 可能带品类/产品线后缀(如 `Waterdrop Water Purifier`、`Bewinch`),榜单与其他展示位置用 `displayBrand()` 剥掉后缀,让客户读到品牌本身;**别名匹配仍用全称**,精简只发生在展示层,不要在数据层改 key。目标品牌展示时保留 `★` 标记,清洗后回落原名。
- **品牌 logo 取不到时显示首字母占位块**(`entity-logo-fallback`),保持行对齐——原来用 `this.remove()` 会留出空白、把整行撑歪。`onerror` 属性值用双引号包裹时,内部双引号必须转义成 `&quot;`。
- 筛选项:诊断意图用下拉框;「国家」统一叫**「地区」**;搜索框加宽。
- 同一个问题的不同平台 / 地区 variant tab 放**抽屉顶部**;主题汇总行默认展开。
- 排名均值只统计实际提及的问题,未提及的记录不得拉低口径。
- 指标名对外统一用**「发现类问题」**,不写「可见度问题」,也不写「通用回答」等虚构口径。
- 内容规划文案**固定口径,不随品牌数据变化**;第三方阵地先社区(Reddit / LinkedIn),不承诺具体见效时间,只写执行事项与持续监测。
- **术语定稿**:阶段链条写「诊断 → 生产 → **信源分发** → 周期复测」,正文用「内容分发」——「铺设」被客户判定为怪。指标与字段用「引用份额」「平均提及位置」等定稿名,不用废弃叫法。
- **跨平台解读只讲共识**:跨平台对比的目的是看共识,不是给每个平台定独立优化目标。**所有平台差距不大才算有共识**;否则说明没有共识并点名最高的那个平台(Google 系对 YouTube 的引用偏好可作为已知特例提及)。原话「跨平台对比用于识别共识与分歧,单一平台的高低不构成独立优化目标」被客户判定太硬,改写为「怎么看」的柔性表述。
- **情感标签指向产品属性,不指向评价行为**:「第三方评测不占优」不能作为标签,应拆到具体属性上——客户原话「负向,但针对的是那三个属性,不是评测本身」。程度词用「较差」等客户可接受的措辞,避免「不占优」这类模糊判断。
- **「综合推荐」不是主题**:它属于非属性维度(口碑/营销),不进入主题矩阵的行;主题矩阵只放客户真正横向比较的产品属性维度,归不进任何属性的 claim 落到「其他」且不展示。

## 品牌识别与展示范围(两个模块口径不同,不要混用)

| 位置 | 识别范围 |
|---|---|
| 回答详情(抽屉)的品牌提及 | **全量识别**:本品 + 配置竞品 + 开放词表里所有可识别到的品牌 |
| 可见度板块的榜单/占比 | 只展示 5 个(目标品牌 + 3 配置竞品 + 1 个按提及率取到的开放竞品) |
| 回答情感(抽屉内) | 只在**指定品牌集**内判读展示——该回答提到了指定品牌里的哪个,才展示哪个的正负向 |

- 抽屉的品牌提及必须全量,因为它直接决定品牌提及率排名与声量份额的统计基础(客户原话:「品牌提及不是识别所有可识别的本品+同类竞品品牌吗?为什么没识别,你应该全量检查一下哦,这会影响品牌提及率排名和声量份额的统计」)。
- 指定品牌集 = 目标品牌 + 3 配置竞品 + 已确定的开放竞品;**可见度板块与情感板块的品牌集必须一致**——要么都加同一个开放竞品,要么都不加。客户原话:「可见度板块没有 Philips,所有可见度和情感板块要么都不加要么都加」。
- `—` 与空值的含义见 [数据契约](report-data-contract.md) 的 `records[].sentiment` 与 `details[key].sentiment` 两条。

## 验证

- 脚本化遍历 tab 时,**每次点击前重新 querySelector**:tab 按钮每次切换都被 `buildTabs()` 用 innerHTML 重建,开头缓存的引用第一次点击后即失效、后续点击静默无效(Bewinch 案例两轮「45 切片全通过」实际只测了一个切片)。
- 改了 JS / CSS 后必须重做浏览器验证:逐层切国家 / 平台 / 主题,确认各模块有数、无空白、无变形。
