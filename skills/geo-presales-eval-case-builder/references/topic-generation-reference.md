# Case 主题生成规则

## 主题、属性与标签边界

把 Topic 作为纵向主组织：回答“长期独立监测哪个市场、场景或战略机会”，并能自然展开为一组任务、条件和问法不同的 Prompts。把 Attribute 作为横向战略认知：回答“希望 AI 在这些 Topic 中如何认识品牌”，通常是能力、特征或评价标准，可跨 Topic 复用。把 Tags 留给下游 Prompt 的自由分类，例如诊断意图、Branded / Non-Branded、购买阶段及 Attribute 关联。

按以下顺序判断一个候选：

1. 候选是否代表完整的市场、Use Case、ICP 或战略机会，并值得长期单独查看表现？
2. 候选下能否形成一组真实且不同的 Prompts，而不是只靠同义改写？
3. 它是否会明显改变目标客户、核心任务、评价标准、候选品牌或优化动作？

三项成立时保留为 Topic。候选只是多个 Topic 共有的能力、特征或评价标准时，将它保留在 Case 原业务字段供 Prompt Builder 派生 Attribute；无需在 Case 中创建 Attribute 配置。诊断意图、是否提及品牌或其他横向分析维度由下游 Tags 承载，不生成对应 Topic。

## 字段如何参与主题生成

| 字段 | 对主题的作用 |
|---|---|
| 品类 | 定义核心购买集合，通常是宽泛主题的起点。 |
| 垂直行业 | B2B 行业语言，标准或候选品牌明显变化时，可形成细分主题。 |
| 目标客户 | 角色或人群改变购买任务与选择标准时，可形成独立主题。 |
| 痛点 | 对应长期，可投入且会改变选择的解决机会时，可形成细分主题。 |
| 使用场景 | 实际任务明显改变候选集合，评价标准或内容行动时，优先作为细分主题。 |
| 产品特性 | 只在某项硬指标构成完整、可独立监测的购买机会时参与 Topic 命名；普通能力、参数和跨 Topic 评价标准留作下游 Attribute。 |
| 差异化优势 | 用于判断机会是否值得投入，不直接把厂商卖点写成主题。 |
| 适用边界 | 排除邻近但不属于当前 Case 的购买集合。 |
| 补充内容 | 只补充其他字段无法表达的购买路径，地域，季节性或比较边界。 |

## 五维拆分判断

| 维度 | 判断问题 |
|---|---|
| 目标客户 | 提问者，影响者或采购角色是否改变？ |
| 核心任务 | 客户实际要完成的事情是否改变？ |
| 评价标准 | 会改变选择的标准是否明显不同？ |
| 候选品牌 | 买家会比较的品牌集合是否改变？ |
| 优化动作 | 表现差时需要补的页面，证据或渠道是否改变？ |

核心项明显不同才拆分；只有词面，参数，材料，型号或问题形式变化时合并。`partial` 必须写清交集与边界。

## 数量与类型

- “主题”字段允许 1–3 个值，至少填写 1 个，多个值用 `，` 分隔；逗号只放在不同主题之间，主题名称内部尽量使用“和”“或”或“；”，不要使用逗号或顿号。
- 宽泛 Coverage Topic 扫描核心品类整体候选和竞争格局；名称优先使用最短且可识别的品类表达，不能只是行业名或全部业务线拼盘。
- 细分 Depth Topic 聚焦值得持续投入的具体人群，场景或产品机会，必须改变至少一项核心购买判断；名称可比 Coverage Topic 稍长，但只增加一个必要限定。
- 宽泛 / 细分数量不限；没有足够商业差异时只保留一个或两个。

## 命名与可生成性

- Topic 名应简洁，通常 2–5 个词，优先 2–4 个词；只表达一个核心主题。词数用于控制信息密度，不对中文机械按空格或字符计数。
- 使用中文自然名词短语。Coverage Topic 优先只写核心品类；Depth Topic 仅在受众，任务或场景确实改变候选品牌，评价标准或优化动作时，增加其中一个限定。
- 具体受众，使用场景，评价标准，价格，材料，地域和其他约束条件优先放入 Prompt 或下游 Attribute。不得把多项限定串成 Topic，也不得为了显得具体而复述完整购买问题。
- 不写完整问句，不含监测品牌，Best，Top，单个客户，节日或单一 SKU。
- 每个主题应能形成多条条件不同的真实购买问题，并支持目标品牌与已确认竞品在同一条件下比较。
- 若只能靠同义改写或跨品类凑问题，应合并，放宽或拒绝候选。

## 命名判断顺序

1. 先写能代表购买集合的最短核心品类名，作为 Coverage 候选。
2. 只有五维拆分判断成立时，才生成 Depth 候选，并保留一个最能解释差异的受众，任务或场景限定。
3. 把其余能力、评价标准和限制条件保留在 Case 原字段，交给后续 Attribute 规划与 Prompt；删除后不改变 Topic 所代表的购买集合，就不留在名称中。
4. 复查名称是否像栏目名而不是问题：能自然承载多条不同 Prompt 才保留。

长度不是硬门槛。超过 5 个词时必须逐项删除可下沉到 Prompt 的限定；若精简后会失去购买集合边界，可保留稍长的 Depth Topic，并在候选记录中说明原因。

## 工作记录与 Case 写入

候选记录 `selected / merged / rejected / needs_confirmation` 及原因；被判为横向 Attribute 的候选记录 `routed_to_attribute` 及其 Case 来源字段。正式 Case 只写 1–3 个选中主题的名称，不输出宽泛或细分标签。Case Builder 不创建 Attribute 配置、Attribute ID、逐题 Tags 或 Prompt 配额；这些由 Prompt Builder 从 Case 字段派生。
