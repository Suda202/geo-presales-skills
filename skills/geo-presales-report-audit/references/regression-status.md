# 回归状态口径

## 已修复

同时满足以下条件才使用：

- 当前报告存在能够触发历史失败条件的样本。
- 已核对原题、回答、结构化结果和受影响页面。
- 原问题在当前版本没有复现。
- 预期字段或页面结果正确。

在复现证据中写明当前 Task、记录号和正确结果。不能只写“本轮未发现”。

## 修复失败

满足任一条件时使用：

- 当前报告再次出现同一失败机制。
- 已上线的修复在对应样本上仍给出错误结果。
- 一处修复后问题转移到同一链路的另一环节，客户结果仍不正确。

保留当前失败样本，不只引用历史案例。

## 待验证

使用场景：

- 当前报告没有覆盖触发原问题所需的样本。
- 页面版本、数据版本或必要明细无法确认。
- 有疑似样本，但证据不足以排除合理解释。

写清缺少什么样本或证据，以及下次需要如何验证。没有复现不等于已修复。

## 待修复

使用场景：

- 问题已经由当前一手证据确认。
- 尚未进入修复或修复版本尚未提供。

同时给出独立回归的预期结果。

## 后续优化

使用场景：

- 当前结果基本正确。
- 存在可读性、覆盖度、稳定性或低影响体验改进。
- 不会直接改变客户核心指标或判断。

不要用“后续优化”弱化已经造成错误结论的问题。

## 不处理

使用场景：

- 复核后确认不是系统问题。
- 属于第三方模型正常输出或合理证据保留。
- 限定条件、受众变化或场景变化合理，且没有改变购买对象。
- 用户明确接受某项无法稳定获取的结果，例如偶发抓不到有效回答。

在证据中写清为什么不成立，防止同类误报反复进入待修复列表。

## 状态变更规则

- 保留历史记录的状态语义，不用新 Task 证据覆盖旧截图。
- 新 Task 出现可独立回归的失败样本时，优先新增或拆分记录，再关联根因。
- 从待验证改为已修复时，必须补充能够真实触发失败条件的当前样本。
- 从待修复改为修复失败时，必须说明验证的是哪个修复版本或当前版本。
- 任何状态变更都同步更新证据、来源报告和截图。
- 写入后重新读取整条记录，确认状态与证据没有互相矛盾。
