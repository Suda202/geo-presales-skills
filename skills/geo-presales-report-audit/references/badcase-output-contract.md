# Bad Case 交付契约

## 1. 合格记录的硬门槛

每条记录必须同时满足：

1. 标题说人话，让未参与排查的人一眼看懂。
2. 标题写 `Task <编号> + #<记录编号>`；报告级问题写 Task 和具体数字。
3. 说明本来应该是什么、实际变成了什么。
4. 引用原题、回答、结构化字段或页面数字中的具体例子。
5. 填写错误类型、模块、状态和优先级。
6. 上传该 Case 自己的标注截图。
7. 截图画面内写明问题，并用红框、箭头、下划线或编号中的至少一种指向原始证据。

任一项缺失，都不算可交付的 Bad Case。

## 2. 一条 Case 一行

默认拆分以下情况：

- 记录号不同，能够独立修复或回归。
- 根因相同，但实际购买对象不同。
- 实体、失败环节或期望结果不同。
- 需要不同修复规则或验收方式。

只有失败机制、修复规则和验收方式完全相同，且合并不会遮蔽具体例子时才合并。

## 3. 字段写法

### Bad Case

使用结构：

```text
Task <编号> #<记录编号>：本来要……，实际却……
```

示例：

```text
Task 123 #4567：报告要评估目标品类供应商，题目却改问另一类服务商
```

报告级问题没有单条记录号时，直接写两边数字：

```text
Task 123：实际只有 36 条 Visibility 样本，页面却显示 40 条
```

不要写：

- 问题配额继续矩阵化。
- 购买集合漂移。
- 实体上下文异常。
- 品牌提及存在问题。
- 题目跑偏。

这些标题没有具体对象和例子，无法直接理解或回归。

### 错误类型

每条必填。优先复用多维表格已有选项，并按最早出错环节选择，例如问题生成、采集、实体识别、竞品归类、排名提取、情绪识别、引用解析、统计聚合或报告展示。

不要根据标题关键词自动选择；先核对原题、回答和结构化结果。如果表内没有合适选项，先说明缺少什么分类，再经确认新增，不能留空。

### 模块

填写最早发生错误的系统环节，不填写最终被影响的页面。原题已错时模块是问题生成；明细正确、汇总错误时模块才是统计或报告。

### 问题与影响

使用两段结构：

```text
问题：本来要评估什么，原题/回答/结构化结果实际是什么。
影响：具体会让哪个指标、排名、风险或客户判断失真。
```

避免只复述错误类型。

### 复现证据

至少包含：

- 当前报告 Task 和记录号。
- 原题关键原文。
- 回答或结构化结果关键原文。
- 页面实际结果。
- 预期结果。
- 当前来源报告链接。

复制原文时保留足以理解上下文的句子，不只截取一个关键词。

### 建议

写成研发能够实现和回归的规则：

- 说明在哪个阶段增加什么判断。
- 说明哪些输入应该保留、排除或降级。
- 给出当前记录的预期结果。

没有可靠修复方案时可以只写需要补充的诊断信息，不编造规则。

### 状态

只按当前证据选择。具体定义见 `regression-status.md`。

### 优先级

按客户影响和传播范围判断，不按研发难度判断：

- P0：直接改变客户身份、购买对象、核心指标或关键结论；会让整份报告失去可信度。
- P1：显著影响一个核心模块或多条记录，客户很容易看到并误判。
- P2：局部样本、次要表达或低频问题，不改变主要结论，但仍需要修复。

不要仅因历史上定过优先级就机械沿用；根据当前 Case 的影响重新判断。

### 问题截图

每条 Case 使用自己的截图，画面至少包含：

- Task 和记录号，或报告级问题所在模块。
- 原题或页面数字。
- 关键回答、结构化标签或聚合结果。
- 一句人话问题说明。
- 指向证据的红框、箭头、下划线或编号。

推荐画面说明：

```text
问题：采购对象从目标品类变成另一类服务
Task 123 · #4567
关键证据：原题要求的交付对象已超出目标品类
```

标注规则：

- 把说明放在新增留白或不遮挡内容的区域。
- 用红框圈出导致问题的关键词、错误数字、错误实体或错误结论。
- 至少使用一种明显标记指向证据，不能让读者自己寻找；复杂画面推荐同时使用红框和箭头。
- 一图有多个证据点时使用 `①②③`，并逐项对应。
- 保留足够上下文，不能裁到看不出 Task、记录号或问题含义。
- 只叠加确定性标注，不使用生成式编辑重写原始证据。

只有原始页面、只有旁注但没有指向证据、或必须打开文字字段后才能理解的截图，都不合格。

### 来源报告

指向当前 Case 所在报告或预览版本，不残留旧 Task 链接。历史链接只在复现证据中作为补充。

## 4. 不要新增的字段

不要新增独立 `Task ID` 或“本轮标记”字段。把 Task 和记录号写进 `Bad Case` 与 `复现证据`，让记录脱离视图后仍能定位。

## 5. 提交前自检

```text
□ 标题是否说人话
□ 标题是否有 Task 和记录号；报告级问题是否写清具体数字
□ 是否写明本来应该什么、实际变成什么
□ 是否给出原题/回答/页面数字的具体例子
□ 错误类型、模块、状态和优先级是否都已填写
□ 是否一条可独立回归的 Case 一行
□ 是否上传该 Case 自己的截图
□ 截图内是否直接写明问题
□ 是否用箭头、框选、下划线或编号中的至少一种指出原页面证据
□ 来源报告是否为当前版本
□ 写入后是否逐条读回
```
