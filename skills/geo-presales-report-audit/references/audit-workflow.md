# 全面审计流程

## 1. 先固定报告身份

记录以下信息：

- Task 编号、品牌、官网、目标市场和目标受众。
- 报告 URL、预览 URL 或 HTML 文件。
- 报告生成时间、预览时间和当前审计时间。
- 历史 Bad Case 表、适用视图和状态字段。

发现预览页和静态报告不是同一版本时分别记录，不用一个版本的截图证明另一个版本的问题。

## 2. 建立数量对账

从页面摘要和明细分别统计。先按 Topic 对账实际问题明细总数，再分别统计问题类型集合包含 `visibility`、包含 `sentiment`、同时包含两者的数量，以及实际有效回答数。

```text
总问题数 = 去重后的 question_id 数
Visibility 样本数 = question_types 包含 visibility 的有效回答数
Sentiment 样本数 = question_types 包含 sentiment 的有效回答数
重叠样本数 = question_types 同时包含 visibility 与 sentiment 的有效回答数
```

Visibility 样本数与 Sentiment 样本数存在交集，不能相加反推总题数。继续核对各模块使用的分母和实际入选 ID：Visibility 与主要引用生态使用包含 `visibility` 的问题；情绪使用包含 `sentiment` 的问题。当前六个诊断意图只作标签分布和专项结果核对，不要求互斥，也不要求合计等于总问题数。

抓不到有效回答可以导致实际样本少于预期配额；这本身不一定需要修复，但客户页面必须展示实际有效数量，不能继续显示预期配额。

区分：

- `0/N`：有样本、结果为零，可以展示 0%。
- `0/0`：没有样本，应展示 `-` 或“暂无数据”，不能伪装成 0%。

### 2.1 区分总数、覆盖数和 Top N 展示

先确认产品设计、字段语义和页面标签，再判断数量是否错误。不要仅因为底层存在超过 N 条记录，就把页面展示 N 条判成“把 Top N 当总数”。

- “热门页面”“Top N”“展示前 N 条”或固定最多展示 N 条属于合法的列表截断；即使底层来源超过 N 条，也不创建数量错误 Case。
- 页面只展示 N 条但没有承诺展示总数时，不从列表长度反推总量，也不要求额外展示总量。
- 原始引用记录数、去重 URL 数、引用该域名的回答数和 Top N 列表长度是不同单位；只有口径、归一规则和样本范围一致时才能直接对账。
- 只有页面明确声称“共 N 个”“已有 N 个全部页面”或存在产品定义的总数字段，而同口径底层结果不是 N 时，才记录统计或展示错误。
- 产品设计已经确认只表达 Top N 时，将历史同类记录标记为“不处理”或按当前证据纠正，不沿用旧报告里的错误假设。

## 3. 逐层阅读报告

按报告顺序检查：

1. 页头、客户身份和任务配置。
2. 数据总览和题量。
3. 品牌提及、竞品与排名。
4. 品牌表达与情绪。
5. 引用来源及官网归类。
6. 机会、风险和行动结论。
7. 问题明细与回答详情。

任何聚合异常都追溯到具体记录号、原题和回答全文。任何明细异常都检查是否已经传播到聚合结论。

## 4. 回归历史问题

为每条历史问题提取“可验证失败条件”，例如：

- 哪类输入触发问题。
- 错误发生在原题、采集、结构化还是聚合。
- 当前报告需要出现什么样本才能验证。
- 修复成功时页面或字段应该呈现什么。

再寻找当前报告中的对应样本。相同词语不代表相同问题；不同词语也可能是同一失败机制。

历史记录很早、当前已有更清晰的新样本时，优先用当前 Task 单独建 Case。只有历史记录有助于解释根因或验证修复时才在证据中关联，不把多个 Task 堆进一个标题。

## 5. 开放式发现新增问题

完成历史回归后，重新按数据链路扫描一次，不看历史标题，至少覆盖以下审计面：

- 配置和品牌身份是否正确。
- 问题类型是否只使用 `visibility / sentiment`，同一问题的双类型是否被完整保留而非二选一。
- 诊断意图是否与问题类型分离；未知自由标签是否被保留，旧六值是否被错误写死为封闭枚举。
- 题目是否仍在采购目标品类。
- 限定条件是否改变了购买对象或凭空宣称品牌事实。
- 看似重复的题是否真的具有相同购买对象、条件和预期答案。
- 品牌别名、同名公司和行业实体是否消歧。
- 自然提及的品牌是否为同类竞品，还是平台、机构、型号、部件或配套商。
- 排名是否与去掉引用链接 title/锚文本后、正文中的品牌实体首次出现顺序一致。
- 正/中/负是否符合回答对目标品牌的实际表达。
- 诊断意图包含 Competitor 时是否独立输出胜者/平局和判断强度；同一问题还含 `sentiment` 时是否另算目标品牌情绪。
- 诊断意图包含 Validation 时是否绑定具体 Attribute 与同 Topic 的 Visibility 样本，并区分“知道”与“主动推荐”。
- Accuracy 是否逐项比较官方真值和回答主张，并标明错误来源。
- Market Perception 是否解释品类选择框架；若同一问题类型还含 `visibility`，是否分别保存两类结果而未互相覆盖。
- 正文链接、引用标记、结构化引用和报告引用列表是否一致。
- 采集控制词是否真的进入客户可见内容或导致正文丢失。
- 明细、模块指标、风险和行动结论是否互相一致。

这些是审计面，不是“必然存在的问题清单”。没有一手证据就不创建 Case。

## 6. 使用通用判定原则

### 6.1 题目是否跑偏

用下列结构理解题目：

```text
目标品类/购买对象 + 买方 + 应用场景 + 约束条件 + 比较对象
```

买方或场景扩大不等于跑偏。判断题目最终要求采购、比较或交付的对象是否仍属于目标品类。

同一根因下，如果实际购买对象、修复规则或回归方式不同，拆成独立 Case。

### 6.2 限定条件是否合理

BOM、产能、温度、项目规模、保修年限和性能门槛可以是合理的假设性采购条件，不要求输入提前证明每个数字。

只有以下情况才记录：

- 条件明显不适用于目标品类或买方。
- 条件把购买对象改变成另一种产品或服务。
- 系统把假设无证据地写成品牌已经满足的事实。

模型回答“缺少公开数据”通常是合理的证据边界，不自动构成 Bad Case。

### 6.3 是否重复出题

不要按主题词或能力名计数。只有同时满足以下条件才判重复：

- 核心购买对象相同。
- 买方、应用、关键约束和比较对象基本相同。
- 预计答案高度重复。
- 差异只是无关措辞。

同一主题加入不同且有效的限定条件，可以代表不同商业意图，不判重复。

### 6.4 品牌实体和同类竞品

区分：

- 客户品牌及别名。
- 同名、同缩写但不同领域的公司。
- 销售输入的正式竞品。
- 回答自然提到的同类供应商。
- 平台、机构、认证组织、型号、部件和配套厂商。

回答可以自然提到任何实体。系统错误通常发生在结构化层把不可替代实体标成同类竞品、参与排名或影响客户指标时。不要把第三方模型的自然回答直接归咎于爬虫。

判定品牌是否在正文中提及前，先构造“去引用正文”：从回答 HTML 中移除引用链接的 title/锚文本，再做实体提取和出现顺序计算。

- 只存在于引用链接 title/锚文本的 `Leap+1`、`GridVest+1` 或来源站名，不计正文品牌提及。
- 同一名称在非链接正文中另有出现时，才作为品牌保留。
- 不能只在已混入链接 title/锚文本的纯文本中搜品牌名。
- `Ltd`、`Limited`、`Inc`、`LLC`、`Corp`、`Corporation` 等公司后缀不得拆成独立品牌。如果历史问题由引用链接 title 触发，则 title 内的完整公司名是有效回归输入：当前结构化结果未将后缀单独抽成品牌时，可判该历史问题已修复。注意区分真实公司后缀和 `limited lifetime warranty` 中表示“有限”的普通形容词。

品牌提及抽取忠实记录回答呈现的候选集合，不替回答重新做采购筛选。回答已经把某品牌列为候选、备选或比较对象时，即使随后认为它不满足某项核心需求、只适合作为替代方案或给出明显限制，也继续计入品牌排名；这些内容进入回答质量、准确性或情绪审计，不用于删除品牌提及。

### 6.5 排名

本产品的“品牌排名”定义为品牌实体在去引用正文中的首次出现顺序，不额外要求回答存在 Top、best、first choice 或明确强弱比较。

审计时按以下顺序复算：

1. 移除引用链接 title/锚文本。
2. 排除产品名、规格、尺寸、机构、平台和独立公司后缀等非品牌实体。
3. 按剩余品牌在正文中的首次出现位置给出 `#1`、`#2`……

只有结构化顺序与这一口径不一致时才记录排名问题。不要把该顺序额外解释为 AI 对品牌优劣或推荐强度的判断。

跨回答输出使用批次品牌词典中的同一规范名。规范名优先沿用本批次已有的稳定、易读写法；官网的全小写、全大写或特殊字形只作参考，不单独构成改名理由。母品牌、子品牌和产品线按回答实际作为候选使用的名称区分，不能只凭隶属关系强制替换。

### 6.6 情绪

只使用正向、中性、负向三档，只判断回答对目标品牌的表达，不判断最后是否采用：

- 正向：明确肯定能力、价值、可信度、表现或候选资格，且正向占主导。
- 中性：主要陈述事实，或正负表达大致相当，没有明显倾向。
- 负向：明确否定能力、表现、可信度或场景适用性，且负向占主导。

“需要验证”“缺少公开数据”“有条件采用”不能自动判中性。结合全文判断这些是证据保留，还是对品牌能力的实质否定。

### 6.7 引用

逐条比较：

- 回答正文的裸 URL、Markdown 链接、脚注或平台来源标签。
- 结构化 quotes 或 citations。
- 报告引用列表。
- 官网域名归类。

正文有有效来源而结构化引用或报告列表缺失，才记录漏采。引用模块为空但正文也没有有效来源，不等于解析失败。

引用页面列表是 Top N 设计时，只检查入选、排序、链接和来源归类是否与产品口径一致；不要拿底层全部唯一 URL 数要求列表完整展示，也不要把列表长度解释为官网页面总数，除非页面或产品字段明确这样定义。

### 6.8 控制词泄漏

看到 `Done` 或类似控制词时继续检查：

- 是否真的展示在客户可见报告。
- 正文是否因此截断或丢失。
- 中文、引用和品牌识别是否受影响。

只存在于内部原文而客户页面正常时，不创建客户报告泄漏 Case。

## 7. 控制误报

在建 Case 前完成反证：

- 是否只是第三方模型正常推理或证据保留。
- 是否只是合理的受众、应用或限定条件差异。
- 是否只看了摘要，没有核对原题和回答。
- 是否混用了不同报告版本。
- 是否把“当前无样本”误当成“已修复”。
- 是否把相关实体误当成可替代竞品。
- 是否把引用链接 title/锚文本误当成正文品牌。
- 是否在产品已定义“出现顺序即排名”时，额外要求明确推荐关系。
- 是否只是普通错别字、缺字、标点、排版或不影响数据与结论的基础文案。

证据无法排除合理解释时，先记录审计备注或待确认，不要直接写成确定性 Bad Case。
